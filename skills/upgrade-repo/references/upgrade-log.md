# Upgrade log

Every skillskit change that affects a **scaffolded repo**, newest first. A repo
created before an entry's date does not have that change until it is upgraded.

`upgrade_repo.py --apply` handles the **Managed** files on its own. The **Manual**
lines are the ones it cannot do: edits to files a repo is expected to customize,
and decisions only the maintainer can make. Read from the top down until the
entries describe things the repo already has.

**Maintaining this log is not optional.** A change to anything under
`skills/create-skill-repo/assets/template/` that is not recorded here reaches new
repos and silently skips every existing one. Add the entry in the same change.

## 2026-08-31 — optional "Built with skillskit" footer

**Why.** Repos generated by the kit had nothing pointing back at it, and a reader who
liked one had no way to find the tooling behind it.

**Managed:** nothing — this is a courtesy, not infrastructure.

**Manual (entirely optional):** add to the end of your README, below the licence:

```markdown
---

[![Built with skillskit](https://img.shields.io/badge/built%20with-skillskit-F5A623)](https://github.com/Paldom/skillskit)

Scaffolded with [skillskit](https://github.com/Paldom/skillskit) — eval-first Agent
Skills tooling. This line is yours to delete; nothing checks for it.
```

It is a provenance statement, not a quality claim: your CI badge already carries the
live gate signal. New scaffolds get it by default (`--no-attribution` opts out) and
`make check` neither requires nor mentions it — in your repo, that is your call.

## 2026-08-31 — the README is part of the product, and part of the gate

**Why.** A skills repo's README is a landing page: the reader arrives from skills.sh
and decides whether to install in about fifteen seconds. Nothing checked it, so
READMEs drifted — a catalogue missing a skill that shipped, examples showing a
script that lives *inside* a skill (implementation detail a user should never type),
flat numbered lists implying every step is mandatory, and no proof of anything.

**Managed** — applied automatically:

- `docs/readme-standard.md` *(new)* — the contract: section order, the icon rule,
  skills-level examples only, demo-as-code, step markers, the deslop scope, and a
  table of exactly which rules the gate enforces.
- `scripts/validate_skills.py` — `check_readme()` enforces the mechanical half:
  icon first and every referenced local image resolving; `npx skills add
  <owner>/<repo>` present; no skill-internal script path (`skills/x/scripts/…`,
  `${CLAUDE_SKILL_DIR}`) inside any code fence; catalogue parity in both directions
  against `skills/`; step markers limited to `Required` / `Optional` / `Afterward`;
  warnings for mixed marked/unmarked steps, missing demo media, and `<details>` or
  GitHub alert syntax (skills.sh strips both). HTML comments are ignored, so
  commented-out guidance is not a broken reference.
- `scripts/test_validate_skills.py` — a conforming README stays silent and each rule
  is asserted to fire.

**Manual:**

1. `README.md` — restructure to the order in `docs/readme-standard.md`. Expect real
   findings the first time; they are the point. Warnings on a fresh repo (no icon,
   no demo) are the TODO list, not a failure.
2. **Icon.** Generate one with the
   [icon-designer-skills](https://github.com/Paldom/icon-designer-skills) pipeline:
   `/icon-brief` → `/icon-draw` → `/icon-critique`, then **you** pick — the critique
   step hands candidates to a human by design. Master SVG to `assets/icon.svg`.
3. **Demo.** Commit the source and the render: `/tape-demo`
   ([terminaltor](https://github.com/Paldom/terminaltor)) for terminal work,
   `/walkthrough-storyboard` + `/walkthrough-record`
   ([screenshooter](https://github.com/Paldom/screenshooter)) for a browser. Neither
   is a dependency of your repo — they are authoring-time skills; the artifact ships.
4. `.local/PROMPT.md` — if you drive sessions with a goal prompt, add the README step
   and the `/deslop` scoping from the template's copy. Deslop runs **last**, on prose
   only, and never on code, commands, flags, paths, numbers, headings, table cells or
   step markers; re-run `make check` after it.

## 2026-08-30 — lint, commit hooks, and a security scan on skill content

**Why.** Skills ship to other people's machines via `npx skills add`, and registry
audits keep finding the same handful of patterns in the wild: payloads piped from
the network into a shell, environments posted to a collector, instructions that
tell the agent to act without telling the user. Nothing in the gate looked for any
of it. The Python the kit ships was also unlinted, so a `shell=True` or an unused
import could reach a scaffolded repo unnoticed.

**Managed** — applied automatically:

- `scripts/validate_skills.py` — now scans each `SKILL.md` **and every script the
  skill bundles** (`.py .sh .bash .zsh .js .mjs .ts`) for: download-piped-to-shell,
  environment-piped-to-network, base64-decoded-to-shell and `shell=True` (errors);
  credential-path references and prompt-injection/user-concealment phrasing
  (warnings). Executable badness errors; judgement calls warn.
- `scripts/test_validate_skills.py` *(new)* — asserts both halves of that: the
  malicious patterns still fire, and the safe lookalikes this kit actually uses
  (`env -u DISABLE_TELEMETRY …`, `curl … -o file`, `… | tee`) still do not. A
  security regex that quietly stops matching is worse than no check.
- `.claude/hooks/lint_python_file.py` *(new)* — PostToolUse hook: ruff check +
  format on every `.py` an agent writes, feeding failures straight back to it.
  Skips silently when ruff is unavailable; CI remains the real gate.

**Manual** — the toolchain config is yours to tune, so none of it is overwritten:

1. `ruff.toml` — copy it from the template. Rules are `E W F I UP B C4 SIM S RUF`;
   `S` (flake8-bandit) is the point of the exercise. `required-version` pins ruff so
   a stale one on someone's PATH refuses to run rather than disagreeing with CI.
2. `requirements-dev.txt` — add `ruff==0.15.10` and `pre-commit==4.3.0`. These are
   dev-only: everything the repo *ships* stays stdlib-only.
3. `.pre-commit-config.yaml` — copy it from the template, then
   `make hooks` (`pre-commit install --install-hooks`). Note `--exit-non-zero-on-fix`
   on the ruff hook: without it ruff fixes the file, the hook passes, and the commit
   ships the *unfixed* content.
4. `Makefile` — add the `lint` and `hooks` targets and put `lint` in `check`.
5. `.github/workflows/ci.yml` — add a ruff step and run `test_validate_skills.py`.
   Everything in the commit hook must also run in CI; `--no-verify` bypasses hooks
   silently.
6. `.claude/settings.json` — add `lint_python_file.py` as a second `PostToolUse`
   command alongside `validate_skill_file.py`.
7. Run `make lint` and expect real findings on code that has never been linted. Fix
   them; where a rule is wrong for a specific line, suppress **at that line with a
   reason** (`# noqa: S603` plus why), never by dropping the rule from `select`.
8. Run `gh skill publish --dry-run` and clear what it reports — secret scanning and
   push protection are repo settings worth enabling regardless.

## 2026-08-29 — trigger evals are executed, and invocation mode is first-class

**Why.** The eval-first rule was only ever shape-checked: a skill could ship eight
positive prompts that all routed to a sibling and the gate stayed green. And the
router rules were applied to every skill, including user-invoked ones that no
router ever weighs — in skillskit's own repo that mis-graded `publish-repo` and
demanded 16 trigger cases nothing would route.

**Managed** — applied automatically:

- `scripts/run_evals.py` *(new)* — scores every trigger prompt against every
  description in the repo: vocabulary overlap, top-K rank against siblings,
  near-duplicate descriptions, a negative that outscores every positive, and a
  `--min-rank1` ratchet. Stdlib only, no model call, no network.
- `scripts/test_run_evals.py` *(new)* — self-check for the scoring logic.
- `scripts/validate_skills.py` — applies the description rules (length floor,
  trigger clause, negative trigger) only to model-invoked skills, and waives the
  trigger-case minimums for `disable-model-invocation: true` skills.
- `docs/skill-authoring.md` — the model-invoked vs user-invoked table, the
  alias-over-engine pattern, and a 25–150 line body target (500 stays the ceiling).
- `docs/evals.md` — what `make evals` checks and, explicitly, what a lexical
  scorer cannot prove.
- `.claude/skills/add-skill/SKILL.md` — picks the invocation mode in step 1,
  before the description is drafted.

**Manual** — the runner does nothing until it is wired in:

1. `Makefile` — add the targets and put them in `check`:
   ```make
   .PHONY: check validate evals test
   check: validate evals test

   evals:
   	python3 scripts/run_evals.py

   test:
   	python3 scripts/test_run_evals.py
   ```
2. `.github/workflows/ci.yml` — after the validator step in the `validate` job:
   ```yaml
   - name: Score trigger evals (routing, collisions)
     run: python3 scripts/run_evals.py
   - name: Self-check the scorer
     run: python3 scripts/test_run_evals.py
   ```
3. `AGENTS.md` — the description convention is now mode-dependent; the body target
   is 25–150 lines. Copy the wording from the template's `AGENTS.md`.
4. Run `make check` and fix what it finds. Expect real failures on a repo that has
   never been scored: a `should_trigger` prompt sharing no vocabulary with its
   description, or two descriptions that have drifted together. **Fix the
   description, not the eval** — the eval is the specification.
5. Once it passes, freeze the number: add `--min-rank1 <a few points under your
   current score>` to the `evals` target. Raise it deliberately as the score
   improves; never lower it to get green.
6. Any skill of yours that is `disable-model-invocation: true` may now drop its
   `should_trigger` / `should_not_trigger` cases and keep only `quality` ones.
